# 注释风格规范（本项目）

> 参考样板：`~/workspace/wt_field/scene/game.gd`、`~/workspace/wt_field/scene/player.gd`
> 本仓范例：`scripts/module/gameplay/model/cell_state.gd`、`scripts/module/gameplay/core/queendoku_core.gd`
> 校验工具：`python3 tools/check_comments_only.py <文件...>`

## 一、绝对红线（只加注释，不碰代码）

1. 不得删除、修改、重排、重新缩进任何一行代码——包括 `var here : Vector2i` 里多余的空格、孤立的 `pass`、原有空行。
2. 不得新增或删除空行。
3. 只允许两种动作：
   - 在一条语句**之前**插入整行注释；
   - 在**单行完整语句**末尾追加 ` # 说明`（`#` 前至少一个空格）。
4. 禁止在跨行结构内部插注释：括号未闭合的多行表达式、函数签名换行、行尾有 `\` 续行符的行。
5. 注释行缩进必须用 **Tab**，与其下方代码的缩进完全一致。
6. 不要动 `.uid`、`.tscn`、`.tres`、`.godot` 等任何非 `.gd` 文件。

自检（必须通过）：

```bash
python3 tools/check_comments_only.py <本次改过的文件...>
# 期望输出：结果：N 个文件全部只增加了注释，代码逐字符一致 ✅
```

## 二、风格

1. **全中文、短句**。说清「这是什么 / 为什么这么设计 / 谁调用谁 / 有什么副作用」。
2. 不翻译代码字面意思，不写废话——`# 循环 i 从 0 到 n` 这种一律不要。
3. 文件第一行写一句职责说明，例如：
   - `# 棋盘格子的状态表：7 个状态常量 + 3 个判断函数，纯数据、无实例`
   - `# 提示引擎：不查答案，真的在解题；R1~R5 五层策略逐级递进`
4. 成员变量按用途分组，组标题用四短横：
   - `# ---- 子节点引用（@onready：进场景树后才可用） ----`
   - `# ---- 运行时状态 ----`、`# ---- 可调参数（Inspector 可改） ----`
   - 组内每个变量尽量加行尾注释。
5. 大类分段用等号横幅，插在原有空行之间（不要为它新增空行）：
   - `# ================= 生命周期 =================`
   - `# ================= 输入处理 =================`
6. 每个 `func` 前加一行 `# 说明`，动词开头，讲职责不讲实现细节。
7. `const` / `enum` / `signal` / `@export` 尽量加行尾注释；数值要写**单位**（秒 / 像素 / 帧 / 次数）。
8. 不写 `##` 文档注释，不写 `@param` / `@return`，不写英文注释。

## 三、准确性要求

- 看不懂的行为不要猜，宁可少写也不写错。
- 有副作用要写明：会写存档、会发某个信号、会改 `Engine.time_scale`、会 `queue_free()`。
- 数值/边界要写清：单位、默认值含义、`-1` 表示「无」这类约定。
- 与项目其他模块的耦合要点明：例如「由 `GamePage` 每帧调用」「数据源是 `BoardView`」。
- 术语沿用项目已有叫法：猫（CAT）、叉（MARK）、草稿（DRAFT）、区域（region）、题库（level bank）。
